12  MINGGU 9 — BASEBALL MODEL III: DESIRE

TipDari “Ini Menarik” menuju “Saya Menginginkan Hasil Ini”

Mata Kuliah: Person-Centered Communication in the AI Era
Tingkat: Mahasiswa Tahun 2
Durasi: 2 jam
Domain: Working Colleagues
Tema Besar: How do we move a person from Interest to Desire without manipulation?

12.1 1. Dari UTS menuju Base 3

Sampai Minggu 8 mahasiswa telah mempelajari dan mempraktikkan:

TARGET → ATTENTION → INTEREST

Target mengatakan:

Attention: “Ya, ini memang masalah atau peluang yang penting.”

Kemudian:

Interest: “Solusi itu kelihatannya relevan. Saya ingin mengetahui lebih jauh.”

Tetapi:

Interested is not the same as wanting.

Seseorang dapat berkata:

“Teknologinya menarik.”

tetapi tidak merasa:

“Saya membutuhkan ini.”

Minggu 9 membahas bagaimana komunikasi membantu person bergerak menuju:

BASE 3 — DESIRE

12.2 2. Baseball Model / TAIDA

Model lengkap:

TARGET → ATTENTION → INTEREST → DESIRE → ACTION

atau:

T → A → I → D → A

Minggu ini kita fokus pada:

[ ]

State awal:

“Saya ingin tahu lebih jauh.”

State yang ingin dicapai:

“Saya menginginkan outcome tersebut.”

12.3 3. Pitch Ketiga

Pitch ketiga dapat diringkas:

“This is how it works, and this is what it can do for you.”

Dalam bahasa sederhana:

“Begini cara kerjanya, dan beginilah keadaan Anda dapat menjadi lebih baik.”

Pitch Desire bukan lagi sekadar:

“Saya mempunyai solution.”

Sekarang kita membantu person:

  1. memahami solution;
  2. membayangkan future state;
  3. melihat benefit;
  4. menilai evidence;
  5. memahami risk;
  6. mengetahui apakah solution benar-benar cocok dengan dirinya.

12.4 4. Learning Objectives Minggu 9

Setelah mengikuti pertemuan ini mahasiswa mampu:

  1. membedakan Interest dan Desire;
  2. mengenali signal bahwa target telah mencapai Interest;
  3. menjelaskan solution mechanism secara cukup jelas;
  4. menghubungkan feature → benefit → value → desired outcome;
  5. menggambarkan current state dan desired future state;
  6. menggunakan demonstration, evidence, story, comparison, dan visualization;
  7. mengenali serta menjawab concern dan perceived risk;
  8. membangun Desire tanpa exaggeration atau manipulation;
  9. membaca response dan mengadaptasi communication;
  10. menggunakan AI sebagai simulator, translator, dan communication coach;
  11. menjaga relationship dan autonomy ketika membangun Desire.

12.5 5. Attention, Interest, dan Desire Berbeda

Mari bandingkan.

12.5.1 ATTENTION

“Ya, reporting manual memang menghabiskan terlalu banyak waktu.”

Person mengakui:

problem.

12.5.2 INTEREST

“Jadi reporting itu bisa dibuat otomatis?”

Person melihat:

possible solution.

12.5.3 DESIRE

“Kalau staff hanya perlu memeriksa hasilnya dan kita bisa menghemat tiga jam setiap minggu, itu sangat membantu kami.”

Person sudah melihat:

value bagi dirinya.

Inilah perubahan penting.

12.6 6. Interest Bertanya “How?”

Interest biasanya bertanya:

“Bagaimana caranya?”

“Bisa dipakai di tempat kami?”

“Ada contoh?”

Desire mulai berkata:

“Ini akan membantu kami.”

“Saya ingin kondisi seperti itu.”

“Kalau benar bekerja seperti ini, kami membutuhkannya.”

12.7 7. Desire Berorientasi Outcome

Ini prinsip penting:

People usually do not desire features. They desire outcomes.

Customer jarang sebenarnya menginginkan:

cloud database.

Ia mungkin menginginkan:

data selalu tersedia.

Mahasiswa tidak benar-benar menginginkan:

notification system.

Ia menginginkan:

tidak melewatkan deadline.

Manager tidak menginginkan:

dashboard.

Ia menginginkan:

melihat keadaan project dengan cepat.

Jadi:

solution is the means; desired state is the end.

12.8 8. Current State dan Desired State

Desire muncul ketika person dapat melihat perbedaan antara:

WHERE I AM NOW

dan:

WHERE I COULD BE.

Model sederhana:

CURRENT STATE → SOLUTION → DESIRED STATE

Contoh:

12.8.1 Current State

Setiap Jumat staff membutuhkan 3 jam menyusun laporan.

12.8.2 Solution

Automatic data aggregation.

12.8.3 Desired State

Draft laporan tersedia otomatis, staff hanya melakukan review selama 30 menit.

Sekarang value menjadi:

visible.

12.9 9. Desire Gap

Kita dapat menyebut perbedaan tersebut:

DESIRE GAP

[ Desire Gap = Desired State - Current State ]

Bukan persamaan matematis literal untuk semua hal.

Ini alat berpikir.

Semakin person memahami:

keadaan sekarang,

dan:

keadaan yang secara realistis dapat dicapai,

semakin jelas alasan untuk berubah.

12.10 10. Tetapi Jangan Membesar-besarkan Gap

Manipulative communicator dapat membuat current state tampak:

jauh lebih buruk,

dan future state tampak:

jauh lebih sempurna.

Contoh:

“Kalau tidak menggunakan AI, perusahaan Anda akan tertinggal total.”

atau:

“Sistem ini akan menghilangkan semua masalah.”

Itu bukan person-centered communication.

Kita menggunakan:

credible gap.

12.11 11. Desired State Harus Milik Person

Kesalahan umum:

communicator mengatakan:

“Anda pasti ingin sistem paling modern.”

Belum tentu.

Person mungkin sebenarnya ingin:

sederhana,

stabil,

murah,

mudah dipelihara.

Karena itu jangan menentukan Desire orang lain.

Tanyakan:

“Kalau problem ini berhasil dikurangi, kondisi yang Anda anggap baik seperti apa?”

Desired state harus:

co-discovered.

12.12 12. Future-State Question

Gunakan pertanyaan:

“Kalau masalah ini selesai, apa yang berubah bagi Anda?”

atau:

“Kalau proses ini dapat dipercepat, waktu yang tersisa akan digunakan untuk apa?”

atau:

“Bagaimana Anda tahu bahwa solution ini berhasil?”

Pertanyaan ini membuat target:

membangun sendiri desired state.

12.13 13. Contoh

Customer:

“Reporting membutuhkan tiga jam.”

Communicator:

“Kalau prosesnya bisa turun menjadi sekitar 30 menit, apa dampaknya?”

Customer:

“Staff bisa menggunakan waktunya untuk mengecek error transaksi.”

Sekarang value bukan lagi:

automation.

Value adalah:

lebih banyak waktu untuk quality checking.

Person sendiri yang mengatakannya.

12.14 14. Feature → Benefit → Value → Outcome

Gunakan empat lapisan.

12.14.1 FEATURE

Apa yang dimiliki solution?

Automatic synchronization.

12.14.2 BENEFIT

Apa yang dilakukannya?

Data tidak perlu dimasukkan ulang.

12.14.3 VALUE

Mengapa penting bagi person?

Mengurangi waktu dan kesalahan.

12.14.4 OUTCOME

Kondisi apa yang menjadi mungkin?

Staff dapat memusatkan waktu pada review dan customer service.

Struktur:

[ Feature Benefit Value Desired Outcome ]

12.15 15. Contoh AI Summary

12.15.1 Feature

AI summarization.

12.15.2 Benefit

Dokumen panjang dapat dibuatkan ringkasan awal.

12.15.3 Value bagi Student

Lebih cepat mengetahui struktur sebelum membaca mendalam.

12.15.4 Desired Outcome

Student dapat menggunakan waktu membaca untuk bagian yang paling relevan.

12.16 16. Contoh Shared Calendar

12.16.1 Feature

Shared calendar.

12.16.2 Benefit

Semua deadline terlihat bersama.

12.16.3 Value

Konflik deadline dapat diketahui lebih awal.

12.16.4 Desired Outcome

Team dapat merencanakan workload sebelum masalah muncul.

12.17 17. Jangan Berhenti pada Benefit Generik

Buruk:

“Ini akan meningkatkan productivity.”

Apa artinya?

Lebih baik:

“Staff tidak lagi perlu menyalin data ke tiga spreadsheet, sehingga sekitar dua jam setiap Jumat dapat digunakan untuk review.”

Specificity membuat Desire:

credible.

12.18 18. HOW IT WORKS

Pada tahap Interest, kita cukup menjelaskan mechanism sederhana.

Pada tahap Desire, person biasanya ingin memahami:

Apakah ini benar-benar bekerja dalam situasi saya?

Maka penjelasan perlu sedikit lebih dalam.

Tetapi tetap:

appropriate to the character.

12.19 19. How It Works untuk Engineer

Engineer mungkin ingin tahu:

architecture,

integration,

reliability,

technical limitations.

12.20 20. How It Works untuk Customer

Customer mungkin lebih ingin tahu:

apa yang harus dilakukan user,

apa yang berubah,

apa yang tetap,

apa yang terjadi ketika ada error.

12.21 21. How It Works untuk Manager

Manager mungkin ingin tahu:

workflow,

responsibility,

resource,

impact,

implementation.

12.22 22. How It Works untuk Finance

Finance mungkin bertanya:

investment,

recurring cost,

saving,

financial risk.

Person sama-sama tertarik.

Tetapi:

Desire language berbeda berdasarkan character.

12.23 23. Layered Explanation

Gunakan prinsip Minggu 4:

Simple first, deeper on demand.

Layer 1:

desired outcome.

Layer 2:

mechanism.

Layer 3:

evidence.

Layer 4:

technical detail.

Layer 5:

limitation/risk.

Jangan memberikan semua layer sekaligus jika tidak dibutuhkan.

12.24 24. Demonstration sebagai Repertoire

Jika memungkinkan:

show the future state.

Misalnya:

Problem:

laporan manual.

Daripada mengatakan:

“Sistem dapat otomatis.”

Tunjukkan:

raw data → klik → report draft muncul.

Sekarang target dapat membayangkan:

dirinya menggunakan solution.

12.25 25. Prototype Membantu Desire

Prototype menjawab:

“What would this actually feel like?”

Contoh:

  • mockup screen,
  • clickable prototype,
  • workflow diagram,
  • sample report,
  • sample chatbot conversation.

Prototype mengubah:

abstract possibility

menjadi:

visible possibility.

12.26 26. Before–After Demonstration

Sangat efektif menggunakan:

12.26.1 BEFORE

8 langkah.

12.26.2 AFTER

3 langkah.

atau:

12.26.3 BEFORE

3 jam.

12.26.4 AFTER

30 menit.

atau:

12.26.5 BEFORE

informasi tersebar di lima chat.

12.26.6 AFTER

blocker terlihat dalam satu board.

Ini membuat:

desired state concrete.

12.27 27. Evidence

Desire membutuhkan confidence.

Person bertanya:

“Apakah outcome itu believable?”

Gunakan evidence seperti:

  • measurements,
  • pilot result,
  • previous case,
  • user feedback,
  • comparison,
  • simulation.

Contoh:

“Dalam test dengan 20 transaksi, waktu rata-rata turun dari 4,5 menit menjadi 1,8 menit.”

12.28 28. Jangan Mengubah Evidence menjadi Janji

Data test:

waktu turun 60%.

Tidak berarti boleh mengatakan:

“Sistem pasti akan menurunkan waktu 60% di tempat Anda.”

Lebih tepat:

“Dalam test awal kami melihat penurunan sekitar 60%. Kita perlu pilot untuk mengetahui hasil pada kondisi Anda.”

Credibility membangun Desire lebih baik daripada:

exaggeration.

12.29 29. Story sebagai Future-State Language

Story dapat membantu person membayangkan outcome.

Contoh:

“Bayangkan Jumat sore. Biasanya staff masih menggabungkan spreadsheet sampai jam lima. Dengan workflow baru, draft laporan sudah tersedia sejak pagi dan mereka hanya memeriksa exception.”

Story menunjukkan:

lived future state.

12.30 30. Tetapi Story Harus Jujur

Jangan menggunakan:

fictional success story

seolah-olah:

real evidence.

Jika hypothetical:

katakan:

“Bayangkan…”

Jika actual case:

katakan:

“Pada pilot sebelumnya…”

Truth tetap penting.

12.31 31. Desire Memerlukan Trust

Person dapat sangat menginginkan outcome tetapi ragu:

“Saya tidak yakin Anda dapat mewujudkannya.”

Maka Desire dipengaruhi oleh:

Expected Value × Trust

Secara konseptual:

[ Desire Perceived Value Credibility ]

Jika value tinggi tetapi credibility nol:

Desire untuk memilih solution kita bisa tetap rendah.

12.32 32. Credibility Bukan Pamer

Credibility dapat dibangun melalui:

  • evidence,
  • clear explanation,
  • honesty,
  • consistency,
  • acknowledgment of limitations,
  • relevant experience.

Bukan hanya:

banyak title dan jargon.

12.33 33. Limitation Dapat Meningkatkan Trust

Contoh:

“Sistem ini cocok untuk pertanyaan rutin dari knowledge base. Untuk complaint kompleks, staff tetap harus mengambil alih.”

Itu mungkin terdengar kurang spectacular.

Tetapi target belajar:

communicator memahami batas solution.

Trust meningkat.

12.34 34. Desire dan Risk

Semakin dekat person menuju action, semakin banyak ia memikirkan:

risk.

Contoh:

  • bagaimana kalau gagal?
  • bagaimana kalau staff menolak?
  • bagaimana kalau data bocor?
  • bagaimana kalau terlalu mahal?
  • bagaimana kalau sulit digunakan?
  • bagaimana kalau vendor hilang?

Desire dapat turun ketika perceived risk tinggi.

12.35 35. Risk Is Part of the Person’s Reality

Jangan menjawab concern:

“Tidak perlu khawatir.”

Lebih baik:

“Concern itu masuk akal. Risiko utamanya memang X. Ini cara kita menguranginya…”

Person-centered communication:

acknowledges risk rather than dismissing it.

12.36 36. Four Common Risks

Untuk mahasiswa, gunakan empat kategori sederhana:

12.36.1 PERFORMANCE RISK

Apakah bekerja?

12.36.2 COST RISK

Apakah terlalu mahal?

12.36.3 EFFORT RISK

Apakah terlalu sulit?

12.36.4 RELATIONSHIP / SOCIAL RISK

Apa dampaknya terhadap orang lain?

Untuk technology juga dapat muncul:

privacy, safety, security.

12.37 37. Risk Reduction Repertoire

Communicator dapat menggunakan:

  • pilot,
  • trial,
  • prototype,
  • phased implementation,
  • guarantee,
  • rollback,
  • training,
  • human oversight,
  • transparent limitation.

Contoh:

“Kita tidak perlu mengubah seluruh workflow. Kita dapat mencoba pada satu tim selama dua minggu.”

Sekarang:

perceived risk menurun.

12.38 38. Trial Membangun Desire secara Etis

Daripada memaksa:

“Percayalah, ini pasti bagus.”

Tawarkan:

evidence-generating experience.

“Mari kita uji kecil.”

Person dapat:

mengalami value sendiri.

Ini jauh lebih kuat dan lebih etis.

12.39 39. Desire dan Affordability

Kalimat pitch awal yang Anda rumuskan adalah:

  1. Saya melihat Anda mempunyai problem/opportunity.
  2. Saya mempunyai solution.
  3. Begini cara kerjanya.
  4. Anda dapat afford it.

Affordability mulai relevan di akhir Desire.

Namun affordability bukan hanya uang.

Seseorang dapat bertanya:

“Can I afford this?”

dalam arti:

  • uang,
  • waktu,
  • tenaga,
  • learning effort,
  • risk,
  • organizational change.

12.40 40. Total Cost to the Person

Jadi lebih luas:

[ Affordability = Money + Time + Effort + Risk + Change ]

Tidak perlu dianggap formula numerik.

Tujuannya:

melihat feasibility dari sudut person.

12.41 41. “Murah” Menurut Siapa?

Rp1 juta mungkin:

murah bagi organisasi besar,

tetapi sangat mahal bagi mahasiswa.

Tiga jam training mungkin:

ringan bagi satu person,

tetapi berat bagi team yang sedang deadline.

Affordability harus:

person-centered.

12.42 42. Desire Bukan Sekadar Emotion

Kata Desire dapat terdengar sangat emosional.

Tetapi dalam framework ini Desire berarti:

person now prefers the proposed future state strongly enough to seriously consider pursuing it.

Desire dapat dibentuk oleh:

  • rational benefit,
  • emotion,
  • identity,
  • convenience,
  • trust,
  • values.

12.43 43. Logical Desire

Manager dapat berkata:

“Penghematan 10 jam per minggu membuat solution ini masuk akal.”

12.44 44. Emotional Desire

Parent dapat berkata:

“Saya ingin anak saya merasa aman menggunakan sistem ini.”

12.45 45. Value-Based Desire

Citizen dapat berkata:

“Saya menginginkan solution yang tidak mengorbankan privacy.”

Semua valid.

Karena person:

lebih besar daripada economic calculator.

12.46 46. Desire dan Narrative Character

Character mempengaruhi:

what counts as value.

12.46.1 Engineer

Value:

technical quality.

12.46.2 Manager

Value:

coordinated performance.

12.46.3 Customer

Value:

desired outcome.

12.46.4 Parent

Value:

wellbeing.

12.46.5 Citizen

Value:

fairness and public good.

Jadi Desire Pitch harus bertanya:

What would this character value?

Kemudian:

verify through communication.

12.47 47. Jangan Mengasumsikan Value

Jangan berkata:

“Sebagai manager, Anda pasti ingin mengurangi staff.”

Manager mungkin justru ingin:

mempertahankan staff tetapi mengurangi pekerjaan repetitif.

Tanyakan.

Person-centered approach:

hypothesize → communicate → verify.

12.48 48. Desire dan Identity

Kadang person tertarik karena solution cocok dengan:

siapa ia ingin menjadi.

Contoh:

Seorang team leader mungkin menginginkan tool bukan hanya karena:

lebih cepat,

tetapi karena ia ingin menjadi:

leader yang transparan dan tidak micromanage.

Ini menunjukkan relationship antara:

narrative character dan Desire.

12.49 49. Tetapi Identity Tidak Boleh Dieksploitasi

Manipulatif:

“Kalau Anda benar-benar peduli pada tim, Anda harus membeli sistem ini.”

Itu menyerang identity untuk memaksa keputusan.

Lebih baik:

“Anda tadi mengatakan transparency penting bagi team. Salah satu benefit pendekatan ini adalah status pekerjaan dapat terlihat tanpa harus terus menanyakan setiap anggota.”

Hubungkan pada:

stated value,

bukan pressure.

12.50 50. Interest Pitch vs Desire Pitch

12.50.1 Interest Pitch

“Ada cara membuat reporting otomatis.”

Objective:

membuat person ingin tahu.

12.50.2 Desire Pitch

“Data transaksi dapat dikumpulkan otomatis setiap malam. Draft laporan tersedia pagi Jumat, sehingga staff yang biasanya menghabiskan tiga jam menyusun data dapat fokus memeriksa exception. Dalam prototype, proses review membutuhkan sekitar 30 menit.”

Objective:

membuat person melihat future state dan value.

12.51 51. Desire Pitch Formula

Gunakan formula sederhana:

12.51.1 1. RECONNECT

“Tadi Anda mengatakan…”

12.51.2 2. EXPLAIN HOW

“Cara kerjanya…”

12.51.3 3. SHOW FUTURE STATE

“Dengan begitu…”

12.51.4 4. PROVIDE EVIDENCE

“Dalam test/example…”

12.51.5 5. ACKNOWLEDGE RISK

“Batas/risiko yang perlu diperhatikan…”

12.51.6 6. CHECK VALUE

“Apakah outcome seperti ini cukup berarti bagi Anda?”

12.52 52. Contoh Lengkap

“Tadi Anda mengatakan staff menghabiskan sekitar tiga jam setiap Jumat untuk menggabungkan laporan. Sistem ini mengambil data yang sudah dimasukkan selama minggu berjalan dan membuat draft laporan otomatis. Staff tetap memeriksa sebelum dikirim. Dalam prototype dengan data minggu lalu, draft dapat dibuat kurang dari satu menit dan review sekitar 30 menit. Risiko utamanya adalah format input harus konsisten, jadi kita perlu memastikan template sederhana untuk semua divisi. Kalau waktu reporting bisa turun seperti ini, apakah perubahan tersebut cukup bernilai bagi tim?”

12.53 53. Last Question Matters

Perhatikan:

“Apakah outcome ini cukup bernilai bagi Anda?”

Jangan mengasumsikan.

Biarkan person:

evaluate.

Jika jawab:

“Ya, itu akan sangat membantu.”

Desire signal.

Jika:

“Tidak terlalu. Masalah kami sebenarnya accuracy.”

Kembali:

adapt.

12.54 54. Signal Desire

Beberapa signal:

“Kami benar-benar membutuhkan ini.”

“Ini akan menghemat banyak waktu.”

“Kalau bisa seperti itu, saya ingin mencoba.”

“Ini cocok dengan yang kami cari.”

“Bagaimana kita menerapkannya?”

Yang terakhir bahkan mulai mendekati:

Action.

12.55 55. Signal Masih Interest

“Menarik.”

“Bagaimana technology-nya?”

“Apa ada contoh lain?”

Person masih:

evaluating possibility.

Jangan memaksa menganggap Desire sudah tercapai.

12.56 56. Signal Concern

“Saya suka idenya, tetapi…”

Ini bukan rejection.

Sering berarti:

Desire + Barrier.

Contoh:

“Saya suka idenya, tetapi staff saya tidak punya waktu belajar.”

Sekarang tugas communicator:

memahami barrier.

12.57 57. Desire + Barrier

Kita dapat melihat:

[ Desire to Act = Desired Value - Perceived Barrier ]

Sekali lagi bukan persamaan literal.

Jika value tinggi tetapi barrier juga sangat tinggi:

Action belum terjadi.

Minggu 9 membangun Desire dan mulai mengenali barrier.

Minggu 10 akan membawa kita menuju:

Action and Agreement.

12.58 58. Do Not Fight Objections

Objection adalah:

information.

Customer:

“Kelihatannya terlalu rumit.”

Jangan:

“Tidak, gampang kok.”

Tanya:

“Bagian mana yang terasa paling rumit?”

Mungkin concern:

training.

Sekarang conversation menjadi lebih precise.

12.59 59. Objection Categories

Gunakan lima kategori mudah:

12.59.1 VALUE

“Saya tidak melihat benefit-nya.”

12.59.2 TRUST

“Saya tidak yakin ini bekerja.”

12.59.3 COST

“Terlalu mahal.”

12.59.4 EFFORT

“Terlalu sulit diterapkan.”

12.59.5 RISK

“Saya khawatir jika gagal.”

Masing-masing membutuhkan communication berbeda.

12.60 60. Objection Bukan Musuh

Jika customer bertanya:

“Bagaimana privacy-nya?”

Itu dapat berarti:

ia cukup tertarik untuk memikirkan real implementation.

Pertanyaan kritis sering merupakan:

advanced engagement.

12.61 61. AI sebagai Desire Simulator

AI dapat memainkan character yang sudah berada di Interest.

Prompt:

“Anda adalah manager yang tertarik dengan solusi saya, tetapi belum yakin cukup bernilai untuk mengubah workflow team. Anda khawatir terhadap training, reliability, dan disruption. Jangan langsung setuju. Saya akan mencoba membawa Anda dari Interest ke Desire.”

Mahasiswa harus:

discover which barrier matters.

12.62 62. AI sebagai Future-State Translator

Mahasiswa dapat memasukkan technical feature.

Contoh:

automated log anomaly detection.

Minta AI:

“Jelaskan kemungkinan future state untuk system administrator, manager, dan customer tanpa exaggeration.”

Kemudian mahasiswa mengevaluasi.

12.63 63. AI sebagai Evidence Critic

Minta:

“Apakah evidence berikut cukup mendukung claim saya? Mana yang masih terlalu kuat?”

Ini membantu mahasiswa membedakan:

evidence

dari:

overclaim.

12.64 64. AI sebagai Objection Generator

AI dapat memberikan:

  • cost objection,
  • trust objection,
  • usability objection,
  • ethical objection.

Mahasiswa belajar:

tidak defensif.

12.65 65. AI Bukan Mesin Manipulasi

Tidak:

“Cari kata yang membuat orang merasa takut kehilangan kesempatan.”

Lebih baik:

“Bantu saya membuat future state dan trade-off lebih mudah dipahami sehingga person dapat menilai solution secara informed.”

Prinsip:

AI should improve informed desire, not manufacture desire.
